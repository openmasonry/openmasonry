# Security Policy

OpenMasonry's integrity depends on its verifier, its keys and its witnesses. We treat security reports as the work of the 30th degree (Kadosh, Guardian against Capture), whether or not the reporter is a member.

What to do when something has already gone wrong (a lost or stolen key, a compromised witness, a lost host, a flaw found after genesis) is in the [recovery runbooks](docs/operations/RECOVERY.md).

## Reporting

Open a **private security advisory** on GitHub (Security → Report a vulnerability). Please do not open a public issue for an unfixed vulnerability. A flaw not yet repaired is one of the few secrets Landmark II permits; once it is fixed, the fix and the advisory are public.

Include: the affected file and function, a reproduction (ideally a ledger that `bin/om verify` wrongly accepts or wrongly rejects), and impact.

Reports are received by the Custodian under the [Custodian's charter](docs/governance/CUSTODIAN.md). A flaw in the protocol core is repaired by amendment, never by a quiet change: the procedure is in [RECOVERY.md](docs/operations/RECOVERY.md).

## Conduct reports

A report of harassment or another breach of the [Code of Conduct](CODE_OF_CONDUCT.md) is not a vulnerability, but it travels the same private way: open a private security advisory and say that it is a conduct report. The moderators (members of the 10th degree and above), and until they exist the Custodian under the [Custodian's charter](docs/governance/CUSTODIAN.md), receive it. The public record of any act that follows never names the person who reported.

## Scope

- the verifier (the pinned core of `src/openmasonry/`, run as `python -P -m openmasonry.verify`): any history that verifies but violates the rules of the specification ([SPEC.md](docs/whitepaper/SPEC.md)), any rule the specification and the code state differently, or two machines reading the same files differently;
- the Tyler workflows (`.github/workflows/judge.yml`, `.github/workflows/tyler.yml`): anything that lets a PR influence the code that judges it (the `judge` job runs base-branch code via `pull_request_target` and must only read the PR as data), smuggle a non-ledger change into an auto-merged ledger PR, or satisfy the required `judge` check without the real judge;
- the `@protocol` pin and governed files: any way to change them without a passed amendment. `@protocol` covers the files listed in the manifest `src/openmasonry/protocol.manifest` (the verifier's core, the manifest itself and the three workflows, `judge.yml`, `pages.yml` and `tyler.yml`), which is read from the tree being judged, and the set of workflows is closed: a tree with a file under `.github/workflows/` that its manifest does not list is unlawful. In scope too: any way to change the manifest (add a file, drop one, or get a malformed one accepted) without the amendment that ratifies the resulting digest. The rest of the code changes by code-owner review, so also in scope is any way for that unpinned code, or for a file a PR can add, to run inside the judge or to change what the pinned verifier decides (an import from the core to outside it, a module that shadows a pinned or a standard one), and any way to get a workflow that the manifest does not list past the judge;
- the witness node (`node/`): it must run the verifier baked into its image, refuse to sign when governed files differ or when its own code is not the pinned core, and never write beside an open pull request of its own that could still merge;
- the approval path (`src/openmasonry/actions.py`): any way for an agent or another process to get an act signed without the person confirming it in the dialog, to get a different act signed than the one shown, or to learn a vote chosen there; the dialog bypass must work only in test mode (`OM_CONFIRM`, a marker file in an `OM_HOME` under the system temporary directory, the signing key inside that `OM_HOME` and never under `~/.ssh`, and a scratch ledger);
- admission by invitation (`ledger._invite`, `ledger._petition_checks`): any way for someone who is not a member to get an entry accepted without a live invitation signed by a Master Builder, to petition under another login's invitation, or to invite without drawing on the sponsorship budget;
- the judge's online identity check (`src/openmasonry/identity.py`, `verify --pr-author --since --pr-author-id`): any way to push a member's entry from a GitHub account whose numeric id is not the `github_id` the ledger records for that member (other than the entries a witness or a custodian signs with its own key, and a member's `depart` and `rekey_object`, which anyone may carry), to get a genesis accepted from any account but the one `founder_github_id` names in `src/openmasonry/network.toml`, to get an entry merged that is dated more than 6 hours behind or 2 minutes ahead of the judge's clock, to petition, to rekey or to recover with a key not listed at `github.com/<login>.keys`, to rekey or to recover from a GitHub account other than the one the ledger records for the member, to invite a login that is not the GitHub account with the stated numeric id, to petition from a GitHub account other than the invited one, to make the check pass when GitHub cannot be reached, or to use one key for two logins;
- one GitHub account, one member (`State.id_holders`, `ledger._invite`): any way for an account that already has a member record, a live invitation or a pending petition to be invited under another login;
- key replacement (`ledger._rekey`): any way to replace a member's key without that member's current key, to register a key without a signature made by it, to bring back a key the ledger has seen before, or to keep signing with a replaced key;
- signatures (`src/openmasonry/crypto.py`): validity is defined by the protocol and checked in pure Python (SPEC §13), not by whatever OpenSSH is installed. In scope: any `sig` the verifier accepts that those rules do not make valid, a second accepted spelling of one signature, a hardware-key signature accepted without the user-presence flag or for an application other than `ssh:`, a signature of one key type accepted for the other, a proof made for one purpose (a rekey, a custodian key, a revoke key) accepted for another, and any signature that `ssh-keygen -Y sign -n openmasonry` makes with a valid key that the verifier refuses;
- key recovery (`ledger._rekey_recover`, `ledger._rekey_cosign`, `ledger._rekey_oppose`, `ledger._rekey_object`, `ledger._rekey_recover_apply`): any way to give a member a new key with fewer co-signing Master Builders than the rule asks (two after a freeze, three without one and not all of them sponsors while a Master Builder who is not a sponsor exists, or as many other active Master Builders as exist among those who answered within the last year, or, once a request has been open 30 days, those already given and at least one), before its notice (21, 30 or 45 days) has run or after it expired, over the objection of the key the ledger holds (except a final recovery), over the opposition of the Master Builders, or for a membership other than the one it was asked for;
- custodians and corrections (`ledger._correction` and the acts of `ledger.ACTS`, `ledger._correction_object`, `ledger._correction_apply`, `ledger._open_custodian`, `ledger.sunset_reached`): any way for a correction to **grant** anything (admit, advance, appoint, reinstate, sanction, change a vote, a key or a pin); to stay, void or undo an amendment ballot or the ballot that removes a custodian; to take effect without its ground, its public reason, its notice or its custodian signatures; to stay or void a ballot after its reveal window opened; to escape an objection, the limits (five corrections in 30 days and each custodian's share of them, one stay per ballot, one void and one undo per ballot, one halt in 90 days, the cap on frozen keys, ten notes per custodian a day) or recusal (a ballot of the custodian's own member, a ballot that adds a witness, an advancement to the 3rd degree); to keep a member from departing, replacing their own key, stopping a recovery of their own key, voting, or taking part in an amendment ballot or the removal of a custodian, during a freeze or a halt; any entry accepted from a custodian key after it lapsed, was revoked, was removed, reached the Sunset or the end of its term; any way to create a custodian, or give one a new key, other than a founder's claim under its conditions (`ledger._custodian_claim`: no live key, before the Sunset, fewer than three active Master Builders who are not founders, 30 days of notice that one such Master stops; after an objection, no founder claims again for 30 days; never a founder against whose custodian key a removal ballot passed);
- the reasons of corrections (`govern.missing_reasons`, `govern.stray_reasons`, the judge's exception for `ledger/reasons/`): a correction accepted without its reason in the tree, a reason changed or removed after the fact, or any other file brought into `ledger/reasons/` by a ledger pull request;
- the local verified-signature cache (HMAC-tagged with a private machine key; verify with `OM_NO_CACHE=1` to bypass it);
- the MCP engine (`engines/openmasonry/`): any capability that signs, implements a rule, or passes unvalidated input to `om`;
- the state digest (`State.digest`, SPEC §4.11) and the checkpoint that states it: two states with different stored facts and the same digest, one state with two digests (on another runtime, in another order), or a `witness` entry accepted with a digest that is not the state's;
- the verified-head memory (`ledger.head_verdict`, `actions.canonical_guard`, `node/witness.py`): any way to get a clone or a witness to draft, approve or sign on a canonical ledger that no longer holds an entry it verified, without the person accepting that history;
- post-dated entries: a ledger whose last entry is dated more than ten minutes ahead that the audit (`verify --online`), a witness or `om verify` does not report as `FUTURE HEAD`;
- the candidate-core check (`verify --candidate-root`, the `candidate` job of `tyler.yml`): any change of the protocol core that replays the ledger already kept to a different head or state digest and still passes it;
- the rooms (`src/openmasonry/rooms.py`, pinned, SPEC §15; the room sync `ops/rooms/sync.py` and its GitHub App): a roll that differs from what the ledger derives, a sync that acts on an unverified, rolled-back or post-dated ledger, sends a request outside its closed list, passes its mass guard or invitation caps, touches a protected account, or reads any content of a room;
- the Observatory (`bin/om observatory`, `src/openmasonry/metrics.py`, `src/openmasonry/observatory.py`): a number that is not computed from the ledger (or, for the rooms, from the access the room sync publishes), a page that loads anything from outside itself, or a figure about a single person beyond what the ledger states;
- key handling, ballot secrecy, lot grinding (beacon delay vs. the 6-hour clock tolerance, frozen pools), clock manipulation.

## Response

We acknowledge within 7 days, publish a fix and an advisory, and credit the reporter in the advisory if they wish. A reporter who is a member may also record the report as a `work` entry (`bin/om work <advisory url>`).

## Keys

- **Replace your key when in doubt.** A member replaces their own key with `bin/om rekey --new-key PATH`: the current key signs the entry, the new key signs a proof, and the judge requires the new key to be listed at `github.com/<login>.keys` and the pull request to come from the member's own GitHub account. It can be done once in 30 days, also while suspended, while the key is frozen and while the ledger is halted. The replaced key signs nothing more and can never be registered by a rekey again.
- **Hardware-backed keys are recommended for founders, witnesses and Master Builders** (`ssh-keygen -t ed25519-sk`, with the default application; OpenSSH 8.2 or later and a FIDO2 token). Such a key cannot be copied off its token, and the verifier accepts its signatures only with the user-presence flag, so each act needs a touch. A witness node that signs unattended needs a token that is touched, or a plain key on a dedicated machine: choose knowingly. The protocol checks signatures, not hardware: it records no attestation, so the type of a key is the member's own statement.
- **A stolen key you still hold.** Rekey at once and remove the old key from GitHub.
- **A lost key, or a key in other hands.** The membership is recovered through peers, not through any office ([RECOVERY.md](docs/operations/RECOVERY.md), Constitution Art. X.6). You ask with a new key listed on your GitHub account (`bin/om recover`), from that account. Where a Custodian has frozen the old key (a correction, on the ground `key_compromised`; the urgent case when a thief holds it), two Master Builders co-sign that the person asking is you and 21 days of notice run from the request. A recovery never needs a Custodian: without a freeze, three Master Builders co-sign, not all of them your sponsors while a Master Builder who is not your sponsor exists, 30 days of notice run from the last co-signature needed (the old key is frozen from then on), and the Master Builders may oppose it (`bin/om recover-oppose`). Where fewer other Master Builders exist than the number asked, all of them co-sign (none, for the only Master Builder) and the notice is 45 days; only those who revealed a vote or reported within the last year, or reached the 3rd degree within it, are counted, so where no other Master answers, the recovery rests on your GitHub account, the notice, the old key's objection and any Master's opposition (a thief who holds your GitHub account then takes the membership in about 135 days even if you watch: the old key stops one request, and the final one, 90 days later, applies after 45 days unless a Master Builder opposes it); and a request that still lacks co-signers 30 days after it was made needs only those who have signed (at least one), who may then all be your sponsors, with 45 days of notice: after a freeze they start on that thirtieth day and the old key stays frozen meanwhile; without one, they start on that thirtieth day if the co-signatures then given are enough, and otherwise at the co-signature that makes them enough. While the recovery is open, whoever holds the old key can stop it with one signed entry (`bin/om recover-object`); then the new key completes it (`bin/om recover-apply`), within 60 days of the start of the notice. No Custodian and no ballot replaces a key. If a thief holds the old key and stops the recovery, you ask again, no sooner than 90 days after the stop, and that **final** recovery, which needs three co-signers or as many other Master Builders as exist, cannot be stopped by the old key. A departure, whatever key signed it, is reversed once a recovery completes: a recovery reverses a departure when it is asked before the departure or within 30 days of it, or when it follows, within 150 days of that recovery's request or of the old key's stop of it, a recovery in time for that departure, whatever ended that recovery, so one follow-up may follow another. A Council seat the departure ended comes back only into a vacancy.
- Replacing a key you still hold needs no one.
- **Custodian keys.** A Custodian holds three keys, generated and stored apart: the member key, the custodian key (offline; it signs corrections and the sign of life, and nothing else) and the revoke key (offline, elsewhere; its one power is to remove the custodian key at once). A stolen custodian key is ended by the revoke key, or by the Master Builders' removal ballot; a lost one lapses after 180 days of silence ([RECOVERY.md](docs/operations/RECOVERY.md)).

## Corrections and personal data

The public reason of a correction (`ledger/reasons/<sha256>.md`) and the fields of a `note` are public forever and can never be erased: the tree is unlawful without them. They name no person beyond a login and hold no personal data, and never the identity of a person who reported harm (Constitution Art. XIII.4). Nothing in the verifier enforces this; a reason that breaks it is a matter for objection and for Art. X.

## Known limitations (not vulnerabilities)

- The correction power itself: a deliberate, bounded exception, held by founders named Custodian until the Sunset, and never longer than a term of seven years per key. While few Master Builders exist, corrections are checked above all by publicity and the right to fork (Constitution Art. XVI.13), and where no Master Builder who is not a founder exists, no one can stop a founder's claim of the office.
- No correction while no custodian key is live, and none at all after the Sunset unless the members add one by amendment. A recovery of a lost key needs no Custodian.
- Where the member is the only Master Builder, a recovery rests on the identity gate (the member's own GitHub account and a key it lists), the 45 days of notice and the old key's right to stop one request: nobody co-signs, and the final request, 90 days after a stop, cannot be stopped by the old key, so whoever holds that GitHub account takes the membership in about 135 days even if the member watches (SPEC §12).
- One custodian key is enough for an immediate act, and with a single Custodian for a noticed act too.
- Notice periods are counted from entry times: an entry can be backdated within the 6-hour clock tolerance (the judge allows 2 minutes ahead), and a head dated more than 10 minutes ahead of a reader's clock is an alarm (`FUTURE HEAD`), not a refusal by replay.
- The verified-head memory is a file on one machine: it protects against a rewound repository, not against malware on that machine.
- Votes are public once revealed.
- One witness or none at genesis, and no finality counting of checkpoints yet.
- No attestation of hardware-backed keys, and no ballot that revokes a member's key.
- The Constitution's procedural rules, which the verifier does not enforce (Whitepaper §8.5).
- The Custodian as sole GitHub administrator until the Sunset; and, until the repository is public with a protected `main` branch, no outside forks, no witness auto-merge, and a witness token that could push to `main` directly (it still cannot forge a member's signature).

See Whitepaper §8.3 and §9.2, and the open points of [SPEC.md](docs/whitepaper/SPEC.md) (section 12).
